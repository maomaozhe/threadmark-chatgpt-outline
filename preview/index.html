想系统理解分布式事务，先帮我建立整体认知。

我们先从一个问题开始：当一次业务操作跨越多个服务，怎样让结果保持一致？

1. 分布式事务的整体认知

在单个数据库里，本地事务负责维护原子性。业务拆成订单、库存、账户等服务后，一次购买就涉及多个独立的数据源。

1.1 为什么本地事务不够用？

订单创建成功，而库存扣减失败。每个服务的本地操作都可以是正确的，但业务整体仍然可能不一致。我们需要明确跨服务操作的完成与补偿规则。

先记住一个核心问题

每一步分别成功，不代表整件事最终成功。

1.2 一致性、可用性与业务取舍

先问业务允许多久的不一致，再选择协调方案。支付确认与消息提醒的一致性要求往往不同，统一使用最重的方案通常代价很高。

2. 从业务边界选择方案

2.1 先画清楚一次业务操作

列出参与服务、数据源、关键状态和可逆操作。找到真正需要一起完成的动作，再决定在哪一层协调它们。

结合电商下单，对比一下 2PC、TCC 和 Saga。

还是用“创建订单 → 扣减库存 → 扣款”这条链路。三种方案的差别，在于如何协调提交，以及失败后如何恢复。

1. 两阶段提交：2PC

1.1 Prepare：先询问能否提交

协调者询问各个参与者是否准备就绪。参与者执行本地操作并保留必要资源，向协调者返回准备结果。

1.2 Commit：再统一作出决定

协调者收集所有响应后决定提交或回滚。准备阶段占用的资源、协调者故障和网络异常，是需要理解的工程代价。

2. TCC：在业务层预留资源

2.1 Try、Confirm 与 Cancel

库存服务先冻结库存，再根据业务结果确认扣减或取消冻结。它要求业务自己定义预留、确认和取消的行为。

2.2 幂等与空回滚

重试可能让确认与取消重复到达，所以每一步都需要幂等。取消比预留先到达时，也必须有清晰的处理规则。

3. Saga：用补偿推进长流程

3.1 将业务拆成本地事务序列

每个步骤独立提交，并提供补偿动作。流程失败时按业务规则执行补偿，逐步恢复到可接受的状态。

3.2 补偿不等于时间倒流

已经发送的邮件无法撤回，已经发生的操作也未必完全可逆。补偿是新的业务动作，需要明确边界与失败处理。

如果用消息队列实现最终一致性，应该怎么落地？

可以从“本地消息表 + 可靠投递 + 消费幂等”开始。把难以跨服务原子提交的问题，转成可追踪、可重试的流程。

1. 本地消息表模式

1.1 在同一个事务中写订单和事件

订单记录和待发送的事件写入同一个数据库事务。这样只要订单成功，事件就有持久化记录，不会凭空丢失。

COMMIT;

1.2 异步投递与失败重试

后台任务读取待发送事件并投递到消息队列。发送成功后更新状态。网络超时时结果可能不确定，因此要允许安全重试。

2. 消费端的可靠处理

2.1 通过业务唯一键保证幂等

给事件稳定的业务唯一键，在消费端用唯一约束或处理记录防止重复扣减。重复投递是正常情况，要把它作为设计前提。

2.2 对账、告警与人工兜底

记录失败次数、最后错误和等待时长。对长时间未完成的事件告警，并提供查询、对账和人工处理入口。

一个实用的检查顺序

能否发现失败 → 能否安全重试 → 能否确认完成 → 能否人工处理。

3. 实施清单

3.1 先验证最小闭环

从一条完整链路开始，模拟投递失败、重复消费和消费者重启，再逐步扩展到更多业务。

3.2 再补齐可观测性

让每个事件都有可查询的状态、重试记录和关联订单，方便定位卡在哪一步。
